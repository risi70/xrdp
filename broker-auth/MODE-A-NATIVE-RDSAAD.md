# Mode A - Native RDSAAD Client Mode

Mode A is used when the endpoint client or broker/client stack can produce the
RDSAAD Authentication Request itself.

```text
IGEL / RD Core / compatible RDP client
-> PROTOCOL_RDSAAD
-> Authentication Request PDU with rdp_assertion
-> XRDP BAF validator
-> trusted replay service
-> NSS/SSSD
-> PAM
-> Ubuntu session
```

## Intended Client Behavior

The RDP client negotiates the RDSAAD security protocol and sends the
Authentication Request PDU containing `rdp_assertion`. For clients that expose
Microsoft-compatible RDSAAD configuration, deployments may need to enable the
RDS AAD auth path, for example with an `enablerdsaadauth`-style property where
that property is supported.

The assertion is a BAF compact JWT/JWS generated by the broker or reference
issuer. The client carries the assertion; XRDP does not accept it through the
username or password fields.

## Current Limitation

Mode A is preferred when supported, but it must be proven with actual client
interoperability. Public IGEL / RD Core documentation does not currently prove
that arbitrary custom `rdp_assertion` injection is available to all deployments.
If a client cannot inject or pass the BAF assertion, use Mode B.

## Interoperability Test Plan

1. Configure XRDP with broker-auth, RDSAAD, trusted replay service, trust
   anchor, audience, target, NSS/SSSD, PAM, and `AllowSessionStart`.
2. Generate a BAF assertion with the reference broker issuer.
3. Configure the client for RDSAAD where supported.
4. Connect and capture the security negotiation.
5. Confirm `PROTOCOL_RDSAAD` is selected.
6. Confirm the Authentication Request contains `rdp_assertion`.
7. Confirm XRDP emits `S_OK` only after full BAF authorization.
8. Confirm the Ubuntu session starts as the NSS-resolved Linux user.

Expected packet/protocol observations:

- TLS is established before the pre-MCS RDSAAD exchange.
- Server Nonce is sent by XRDP.
- Authentication Request is received by XRDP with bounded `rdp_assertion`.
- Authentication Result failure is sent for invalid input.
- MCS continues only after `S_OK`.

## Failure Behavior

Malformed JSON, missing `rdp_assertion`, invalid signature, wrong audience,
wrong target, expiry, replay, missing trusted config, replay service failure,
identity binding failure, UID 0, and PAM failure all produce Authentication
Result failure and stop connection progression.

## Non-Primary Mechanisms

CredSSP/NLA, smartcard redirection, WebAuthn redirection, and LoadBalanceInfo
are supporting or alternative mechanisms. They are not the primary BAF
assertion ingress. RDSAAD remains the XRDP-side ingress for Mode A.
